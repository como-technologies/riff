# Review link-01: the maintainer

Issue: #420. Design at commit 56091d2.

## Summary

The direction is right for a maintainer. Today five places connect, try again and show a fault, each in its own way: `Api::send_with` with `busy_waits` (crates/riff/src/api.rs), `follow` with `Reconnect`, `host::in_time` with `CALL_WAIT`, the look of `draw_top` with `Api::reconnected` (crates/riff/src/main.rs), and two copies of the keep-alive loop (`api::keep_alive`, `Tools::keep_alive_every` in crates/riff/src/mcp.rs). One link with one rule removes four of them. Three parts do not work as written. The budget for each process blocks the loops of `chat`, `mcp`, `workers host` and `top`. The `repeat` after a start does not see a call ID that is older than the checkpoint. And the state `refused` ends commands that must wait for a new build. The page also does not say which constants, requirements and book lines go.

## Findings

| link-01-1 | The budget is per process: "a command that runs until stopped has none". But these processes make calls inside one loop, and a call with no end stops the loop. `host.rs` `run`: `Host::answer`, `Host::set_status` and `Host::reap` run in the one `select!` loop. Today `Host::call` stops each call after `CALL_WAIT`, and the module doc says "the host says so and goes on". With no budget, one call during an outage stops the reap of dead workers and the tidy. `chat.rs` `run` awaits `api.post` in its `select!`, so the screen shows no line while the server is down. | link-01-2 | "After a start of the server, a command with the call ID of a record in the last `CALL_KEEP` gets `repeat`." What is good: one rule for a fault and a refusal, which `passes` already has. The drop of the pool after a fault, which only `top` does today. `STREAM_IDLE`: today a stream that died in a sleep has no read limit and can hang. The cursor of `tail`, which removes the read of `chat` at each connect. One text of the state in `text::link_line`. The separate client of the streams (`stream_client`) stays.

## The questions of this point of view

- Fewer places that connect, try again and show a fault? Yes, from five to one, after link-01-1 and link-01-3. Without them the link gets exceptions at each call site again.
- Few rules that a test can check? The rule of section 2 is one table and one diagram: good. The budgets and the state file need link-01-1 and link-01-5.
- Does it fit the code? Most of it moves code that exists: `send_with`, `follow`, `passes`, `replied`, `in_time`. The server part (call IDs, `repeat`, the cursor of `tail`) is new, and link-01-2 is a gap in it.
- The cost of the log change after 1.0.0? Low: link-01-15. The checkpoint change (link-01-2) costs more than the record change.
- The number of constants? Too many as written: link-01-6.
- What goes wrong in a year? A new command calls the link with the wrong budget and holds a loop (link-01-1). The state file shows `offline` after a crash (link-01-5). A refactor of `tail_thread` loses the order of subscribe and read (link-01-9).

## Questions for the lead

- Do `live` and the idle worker move to the heartbeat in this item, or in #424?
