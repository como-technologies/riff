# Review link-03: the skeptic

Issue: #420. Design at commit 56091d2.

## Summary

One link is a good idea, but the three faults of the issue are repaired in the code already. #371: the open watch is no sign of life (`watch` in `crates/riff-server/src/lib.rs`, requirement 01M3WG240PNMQYZ7TX6Z7ZF6M9), and `keep_alive` in `crates/riff/src/api.rs` sends the keep-alive. #379: the streams have a client with no pool (`stream_client` in `api.rs`). #417: `riff top` goes on after a failed look, on a new connection (`Api::reconnected`, `draw_top` in `crates/riff/src/main.rs`). Two gaps are left, and the design repairs them: a call has no time limit (`Api::new` uses `reqwest::Client::new()`, so a tool call of `riff mcp` can hang forever), and a stream that dies with no sign stays open forever (`follow` has no idle limit). The call ID, the state file and the cursor of `tail` repair no fault that happened. They cost about 650 of the 1,550 lines, and one permanent field in the log after 1.0.0. Two rules conflict: `mcp` has no budget, and a refused connect is a refusal but sets the state `up`.

## The questions of this point of view

**What repairs a fault that happened?** The time limits of a call and `STREAM_IDLE`. A dead connection after a change of the address gives a hung call or a hung stream. These two parts repair that. The heartbeat, the separate stream client and the new connection are in the code already.

**Is the call ID worth it?** No. It guards against a double send that only the new tries of the design make (link-03-3). The commands that are not safe are `Release`, `ReleaseFor` and a signed `Post`. Server rules can make them safe (link-03-4). The field in the envelope stays for ever after 1.0.0, for a window of 10 minutes.

**Is the state file needed?** No (link-03-5).

**Is the tail cursor needed?** No. `chat` already reads after each connect, and `top` needs no cursor (link-03-6).

**Is 60 s right?** For a person, yes, with a line after 1 s (link-03-7). For an agent tool call, the design gives no limit at all (link-03-1). Use 60 s for a tool call too.

**Does a drop of the pool hurt many workers?** No. Only drop after a connection fault (link-03-10).

**Does `STREAM_IDLE` match the server?** Yes (link-03-11).

**Rules that conflict or that no test can check:** a refused connect against `up` and against `watch` (link-03-2); "fresh" (link-03-5); the budget against the open try (link-03-8).

## Questions for the lead

- Do you accept "no new try of a command after it may have reached the server", with an error that tells the person to check? Then L4 goes.
- Is a lost line in `riff tail` during a break a fault for you, or is `riff read` enough?
